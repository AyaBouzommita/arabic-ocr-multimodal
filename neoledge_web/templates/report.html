1. The Mission & Challenge

When this internship began, the mission sounded deceptively simple: "Build a system that can extract text from scanned documents." Easy, right? Just install an OCR library and call it a day.

Except our documents weren't simple. They were dense, bilingual administrative papers — Tunisian government forms, university exam sheets, invoices — containing a chaotic mix of Arabic (written right-to-left, with connected cursive letters), French (written left-to-right), and sometimes English, all on the same page. Throw in rubber stamps, handwritten signatures, QR codes, faded ink, and photocopier artifacts, and you have a nightmare that no off-the-shelf OCR tool can solve.

∞ Debugging Hours

The goal was not just to extract text, but to build a complete, production-ready web platform that anyone could use — upload a document, get a perfectly formatted Markdown file back. No technical knowledge required.

"We didn't just want OCR. We wanted a system that could look at a messy, stamped, bilingual Tunisian government document and produce a flawless digital copy — with perfect Arabic spelling, correct reading order, and clean formatting."

2. Research Phase: Choosing the OCR Engines

Phase 1: Engine SelectionWeeks 1–2 — Benchmarking every OCR engine we could find

Our first task was to evaluate every available OCR engine and find the best candidates. We tested three primary contenders on our Arabic and French test documents:

2.1 Tesseract — The Old Guard

Tesseract is the most well-known open-source OCR engine, originally developed by HP and now maintained by Google. We had high hopes for it, especially since Google has been investing in Arabic language support.

The results were devastating. While Tesseract performed admirably on clean, typed English text, it completely collapsed when introduced to Arabic documents:

❌ Tesseract on Arabic

Tesseract couldn't identify Arabic character boundaries. Because Arabic is cursive (letters connect), it broke words into individual, disconnected fragments:

Input:  بسم الله الرحمن الرحيم
Output: ب س م ا ل ل ه ا ل ر ح م ن

✅ Expected Output

What the text should look like — connected, flowing Arabic script with proper word boundaries:

بسم الله الرحمن الرحيم
Verdict: Tesseract was immediately eliminated. Its Arabic support was fundamentally broken for our use case — it treated every letter as an isolated character instead of understanding cursive connections.

2.2 PaddleOCR — The Specialist

PaddleOCR (by Baidu) was our second candidate. Built on PaddlePaddle's deep learning framework, it boasted state-of-the-art accuracy benchmarks across dozens of languages. Our initial tests were incredibly promising:

  • ✅ French documents: Near-perfect accuracy. Clean, precise extraction.
  • ✅ Pure Arabic documents: Surprisingly good. Connected letters were handled well.
  • ❌ Bilingual documents: Complete disaster.

The fatal flaw appeared when PaddleOCR encountered a document containing both Arabic and French text on the same page. Because PaddleOCR processes text in a single directional pass, it couldn't handle the collision between right-to-left Arabic and left-to-right French. Words would merge, reading order would scramble, and entire lines would get swallowed.

2.3 EasyOCR — The Dark Horse

EasyOCR emerged as our Arabic champion. While it wasn't as fast as PaddleOCR, it had a critical advantage: superior bidirectional (BiDi) text handling. EasyOCR could read a line that contained both Arabic and English words without scrambling their order.

The Solution: Dual Pipelines. We made a bold architectural decision: instead of picking one engine, we would use both. PaddleOCR would handle French/Latin documents (where it excelled), and EasyOCR would handle Arabic/bilingual documents (where it was the only engine that didn't break).

3. Layout Parsing: The YOLO Revolution

Phase 2: Layout DetectionWeeks 3–4 — Teaching an AI to see the structure of a document

Even with EasyOCR handling Arabic beautifully, we immediately hit the next wall: layout confusion. When you feed an entire A4 document directly into any OCR engine, it has no idea what's a paragraph, what's a table header, what's a page number, and what's a rubber stamp. It tries to read everything — including decorative borders, watermarks, and signatures — producing absolute garbage.

3.1 The Detector Trials

We needed a "smart eye" that could look at a document and identify distinct regions before running OCR. We tested several object detection architectures:

  • Florence (Microsoft): A powerful vision-language model, but far too slow for real-time document processing. A single page took 8+ seconds.
  • Detectron2 (Meta/Facebook): Excellent for general object detection, but overly complex to configure for simple text bounding boxes. The setup overhead was enormous.
  • YOLO Family: Lightning-fast, single-shot detection. We tested YOLOv8, YOLOv10, and YOLOv11.

3.2 Fine-Tuning YOLOv11s

We ultimately chose YOLOv11s (the "small" variant for speed) and fine-tuned it on a custom dataset of document layouts. We trained it to recognize these specific classes:

Class Action Description
textExtractStandard text paragraphs
tableExtractTabular data regions
lettersExtractIndividual character groups
stampMask (White-out)Rubber stamps that confuse OCR
signatureMask (White-out)Handwritten signatures
pictureMask (White-out)Photos and logos
qr_codeMask (White-out)QR codes and barcodes

The key innovation was the masking step: instead of just ignoring stamps and signatures, we actively white them out from the image before OCR runs. This prevents the OCR engine from accidentally reading random ink patterns inside a stamp as Arabic letters.

Feeding an entire stamped document directly into EasyOCR — the engine reads table borders and stamp ink as letters:

After YOLO crops text regions and whites out stamps, the extraction is clean and precise:

4. The Arabic Crisis: Language Detection

Phase 3: The Hardest Bug We Ever FacedWeeks 5–6 — Why does it work locally but not online?

This section describes what was, without question, the most frustrating and elusive bug of the entire internship. It took multiple days to diagnose and involved three separate root causes that all conspired together.

4.1 The Symptom

When we deployed our Django website to Google Colab and tested it through the online URL, the Arabic extraction completely stopped working. The same document that extracted perfectly on our local Windows laptop would return pure gibberish from the online version — English and French text would come through fine, but every Arabic word was mangled into nonsensical Latin characters.

The maddening part: The exact same code, the exact same image, the exact same models — perfect locally, broken online. We spent hours staring at logs wondering if we were losing our minds.

4.2 Root Cause #1: The Language Sampling Bug

Our pipeline had a "language detection" step that sampled 10 random text boxes from the document to guess whether it was Arabic or French. If the sampling decided it was French, the entire document would be routed to the PaddleOCR French model — which can't read Arabic at all.

The problem? On the exam document we tested with, the top 80% of the page was entirely in English ("Total No. of Questions - 16, Part - II, ARABIC, Paper - I..."). The Arabic questions only appeared in the bottom 20%. Because the sampling algorithm picked boxes from the top of the page first, it found zero Arabic characters and concluded: "This is an English document. Send it to the French pipeline."

❌ Language Detection Failure

Sampling only the top 10 boxes found zero Arabic, so the system thought it was a French document:

Sampled 10 boxes → 0 Arabic chars detected
→ is_arabic_detected = False
→ Routed to PaddleOCR French
→ Arabic text = "WjWWb cllJlB aaaylgalalaylgl"

✅ Fixed: Full-Page PaddleOCR Scan

We replaced the sampling with a full-page PaddleOCR Arabic scan. If even 3 Arabic characters are found anywhere, the Arabic pipeline activates:

Full-page scan → 847 Arabic chars detected
→ is_arabic_detected = True
→ Routed to EasyOCR Arabic+English
→ Arabic text = "طلع البدر علينا"

4.3 Root Cause #2: Missing Custom YOLO Weights

Our fine-tuned YOLOv11s weights file was too large for GitHub (over 100MB). When Colab cloned the repository, the weights file was missing. Without it, YOLO couldn't detect text regions at all, and the pipeline silently fell back to processing the entire raw image — which reintroduced all the layout confusion problems we had already solved.

The fix: We added automatic fallback logic. If the custom weights are missing, the system downloads the standard yolo11s.pt from Ultralytics and uses that instead. Not as accurate as our fine-tuned model, but infinitely better than crashing silently.

4.4 Root Cause #3: Dependency Hell

Our requirements.txt had locked package versions that were incompatible with Colab's Python version. When pip install crashed halfway through, Django and other critical packages were never installed — but the error was buried under hundreds of lines of output, so we didn't notice until the server threw a ModuleNotFoundError.

Lesson learned: Always test your requirements on a clean environment. We ended up unpinning several packages (paddlepaddle, numpy, tokenizers, transformers) to allow pip to resolve compatible versions automatically.

5. NLP Post-Processing: AraBERT & RoBERTa

Phase 4: Teaching AI to Spell-Check ArabicWeeks 4–5 — Context-aware correction using Masked Language Models

Even with YOLO isolating text regions perfectly, and EasyOCR handling Arabic cursive connections, the raw OCR output still contained subtle spelling errors. These weren't random — they were systematic visual confusions caused by Arabic letters that look almost identical:

Correct Letter Confused With Visual Difference
ب (ba)ت (ta), ث (tha)Only the dots change (1 dot below vs 2 dots above vs 3 dots above)
ح (ha)خ (kha), ج (jim)One dot above or below changes the entire letter
د (dal)ذ (dhal)A single dot above changes the meaning completely
ع (ain)غ (ghain)One dot above transforms the letter

Simple dictionary lookup wouldn't work because many of these "misspelled" words actually are valid Arabic words — just the wrong ones. We needed something that understood context.

5.1 The Dual-Model Approach

We built a Bilingual Corrector that uses two separate AI language models:

  • AraBERT (aubmindlab/bert-base-arabertv02) — A BERT model specifically pre-trained on Arabic Wikipedia and news. It understands Arabic grammar, morphology, and contextual word relationships.
  • XLM-RoBERTa (xlm-roberta-base) — A multilingual model covering 100+ languages. It handles French and English corrections.

The correction pipeline works like this:

  1. For each word in the OCR output, check its confidence score.
  2. If confidence is below 90%, mask the word (replace it with [MASK]).
  3. Feed the masked sentence to the appropriate language model (AraBERT for Arabic, RoBERTa for French/English).
  4. The model predicts the most likely word based on surrounding context.
  5. If the prediction has high confidence AND is within an edit distance of 2 from the original, accept the correction.

❌ Raw OCR Output (Before Correction)

هل الحب للوتن لازم ؟
من كان رفيق الغأر ؟
ابن هاجر رسول الله

Note: "للوتن" should be "للوطن", "الغأر" should be "الغار", "ابن" should be "أين"

✅ After AraBERT Correction

هل الحب للوطن لازم ؟
من كان رفيق الغار ؟
أين هاجر رسول الله

AraBERT understood the sentence context and corrected each dotting error perfectly.

6. Image Preprocessing: The Hidden Booster

One of the most underrated improvements came from image preprocessing. Before feeding crops to the OCR engines, we apply a specialized enhancement pipeline optimized for Arabic text:

  1. Upscaling: Small crops (under 128px tall) are upscaled using bicubic interpolation. Arabic diacritical dots are often only 2-3 pixels wide — upscaling makes them visible to the OCR engine.
  2. Bilateral Filtering: Reduces noise while preserving sharp text edges. Unlike Gaussian blur, bilateral filtering doesn't smear thin Arabic strokes.
  3. CLAHE (Contrast Limited Adaptive Histogram Equalization): Enhances contrast locally, making faded ink on aged documents readable again.
  4. Unsharp Masking: Sharpens text edges after the noise reduction step, ensuring that the final crop is crisp and clear.
This preprocessing step alone improved our Arabic Character Error Rate (CER) by approximately 12%. The biggest gains came from upscaling tiny crops — many Arabic dots that were invisible at the original resolution became perfectly detectable after upscaling.

7. Gemini Integration: Markdown Reconstruction

Phase 5: Making It BeautifulWeek 7 — From raw text to formatted documents

At this point, our pipeline was extracting text with excellent accuracy. But the output was just a flat wall of text — no headers, no bullet points, no tables. The original document had rich visual structure that was completely lost.

We integrated the Google Gemini 2.0 Flash API as a dedicated formatting engine. Gemini receives the perfectly extracted text from our YOLO/EasyOCR pipeline and the original document image, then reconstructs the layout into clean Markdown.

7.1 The HTML Injection Problem

Our first attempt hit an unexpected snag. When we asked Gemini to "preserve the layout and maintain right-to-left reading direction," it got creative and started injecting raw HTML tags into the Markdown:

8. The Heavy Model: Qwen2-VL on Cloud GPUs

Phase 6: Bringing in the Big GunsWeeks 7–8 — Running a 7-Billion parameter Vision AI on free cloud GPUs

For extremely dense or degraded documents where even our optimized YOLO+EasyOCR pipeline struggled, we needed a fundamentally different approach. We turned to Qwen2-VL-7B-Instruct — a massive 7-Billion parameter Vision-Language Model by Alibaba that can literally "read" images like a human.

8.1 The GPU Memory War

Qwen2-VL-7B requires 14GB of GPU VRAM just to load. Our local laptop had no GPU. Google Colab's free tier offers a single T4 GPU with 15GB of VRAM. The math was brutal:

14 GB Model Size
15 GB Colab T4 VRAM
1.5 GB Image Processing
💥 Result: OOM Crash

14GB (model) + 1.5GB (processing a dense document) = 15.5GB. Colab only had 15GB. Every single dense document crashed the GPU.

8.2 The Compression Experiments

We tried multiple compression strategies to fit the model:

Strategy VRAM Usage OCR Quality Verdict
4-bit quantization ~4 GB Terrible — hallucinated entire exam questions Rejected
8-bit quantization ~7 GB Poor — misspelled Arabic letters Rejected
Full precision, Dual GPUs (Kaggle) ~14 GB across 2 GPUs Perfect — zero hallucinations Winner
The 4-bit Hallucination Disaster: When we loaded the 7B model with 4-bit compression to save memory, the model completely lost its ability to read text. Instead of extracting the actual French exam questions, it invented its own exam — generating fictional questions about "What is the capital of France?" that didn't exist anywhere on the page!

8.3 The Kaggle Solution

The breakthrough came when we discovered that Kaggle Notebooks offer two free T4 GPUs (30GB total VRAM), compared to Colab's single GPU (15GB). By loading the 7B model with device_map="auto", PyTorch automatically split it across both GPUs — giving us the full, uncompressed model with plenty of headroom for processing.

8.4 The Prompt Engineering Battle

Even with full precision, getting Qwen2-VL to behave as a pure OCR engine required extensive prompt engineering. The model kept trying to be "helpful" in ways we didn't want:

Attempt 1

Long, detailed prompt → Model writes its own exam

When we gave Qwen2-VL a long, conversational prompt about preserving layout and reading direction, it switched into "creative writing mode" and generated fictional French quiz questions instead of reading the actual document.

Attempt 2

Ultra-short prompt ("OCR:") → Model describes the image

When we made the prompt too short, the model treated it as an image captioning task and described the document: "The image is a page from a French language textbook titled..."

Attempt 3

Medium prompt → Model outputs bounding box coordinates

Qwen2-VL is also trained for object detection. When the prompt wasn't explicit enough, it returned pixel coordinates instead of text: (61,31),(992,932)

Final Solution

System prompt + Strict instructions → Perfect OCR

We added a system prompt that explicitly defined its role as "an expert OCR system" and commanded it to "NEVER output coordinates, bounding boxes, or JSON tags." This finally locked it into pure text transcription mode.

9. Deployment: From Localhost to Live Online

Phase 7: Going LiveWeek 8 — Making it accessible to the world

With all the AI models working perfectly, we needed to wrap everything in a user-friendly web application and make it accessible online.

9.1 The Django Web Platform

We built the frontend using Django with a Neo-Brutalist design language — bold yellow accents, thick black borders, and dramatic drop shadows. The interface features a drag-and-drop upload zone where users can submit documents and receive formatted Markdown files.

The platform offers three extraction methods:

  1. Local Pipeline: YOLO → EasyOCR/PaddleOCR → AraBERT → Noise Filter → Markdown output
  2. Gemini Cloud: Sends the image to Google's Gemini 2.0 Flash API for quick, formatted extraction
  3. Heavy Model (Qwen2-VL): Routes the image to a remote GPU cluster running the 7B vision model for maximum accuracy

9.2 The Ngrok Tunnel Architecture

Because we couldn't afford traditional cloud hosting, we engineered a creative solution using reverse proxy tunnels:

  • The Django website runs on Google Colab and is exposed to the internet via Ngrok
  • The Qwen2-VL heavy model runs on a separate Kaggle notebook and is exposed via Cloudflare Tunnels
  • When a user clicks "Extract (Cloud)", the Django server on Colab forwards the image through the Cloudflare tunnel to Kaggle's dual GPUs

9.3 The Tunnel Collision Bug

We discovered that Ngrok's free tier only allows one active tunnel per account. When we tried to run both the Django website AND the Qwen2-VL API on separate Colab notebooks using the same Ngrok account, the second notebook crashed with ERR_NGROK_334: The endpoint is already online.

The fix: We switched the heavy model API to LocalTunnel (and later Cloudflare Tunnels) — completely free alternatives that don't require accounts and have no tunnel limits.

9.4 The Python 3.13 Compatibility Crisis

Just when everything was working, Google Colab upgraded from Python 3.12 to 3.13. Several of our locked package versions (paddlepaddle==2.6.2, numpy==1.26.4) didn't have pre-built wheels for Python 3.13, causing pip install to crash midway through and leaving Django uninstalled. We had to unpin these packages to allow pip to resolve compatible versions automatically.

Key takeaway: Never lock every single package version in your requirements.txt when deploying to cloud environments. Use >= minimum version constraints for packages that frequently update their Python support.

11. Lessons Learned & Conclusion

11.1 What We Learned

🧪 No single model solves everything

We tried to find "the one perfect OCR engine" and failed. The real solution was an ensemble architecture — multiple specialized models working together, each handling what it does best.

🔍 Preprocessing is half the battle

A 12% accuracy improvement came purely from image enhancement — upscaling, contrast adjustment, and noise filtering. No model change, no retraining. Just better input = better output.

🧠 Large Language Models need strict boundaries

Qwen2-VL is incredibly powerful, but without careful prompt engineering and strict decoding parameters, it hallucinated entire exam papers, described images like a museum guide, and output bounding box coordinates instead of text.

💾 GPU memory is the ultimate constraint

We learned that model compression (4-bit, 8-bit) severely degrades OCR quality. The only real solution was finding more VRAM — which led us to Kaggle's dual-GPU setup.

🌐 Deployment is its own engineering challenge

Building the AI was hard. Making it work online was harder. We battled Ngrok tunnel collisions, Colab GPU timeouts, Python version incompatibilities, and dependency resolution failures.

11.2 Future Improvements

  • Fine-tune YOLOv11s on a larger, more diverse document dataset to improve layout detection accuracy
  • Explore newer models like Qwen2.5-VL which offer improved multilingual OCR capabilities
  • Add PDF support for multi-page document processing
  • Implement batch processing for bulk document digitization
  • Deploy to a proper cloud server (AWS/GCP) for production-grade reliability

11.3 Conclusion

What started as a "simple OCR project" evolved into a full-stack AI engineering challenge spanning computer vision, natural language processing, cloud computing, and web development. By aggressively isolating problems across distinct architectural layers — YOLO for layout, dual OCR pipelines for languages, AraBERT for spelling, Gemini for formatting, and Qwen2-VL for heavy lifting — we constructed a system that can handle the messiest, most complex bilingual documents with remarkable accuracy.

"The best OCR system isn't the one with the smartest model. It's the one that knows which model to use, when to use it, and how to clean up after it."
