Internship Report

A comprehensive deep-dive into the struggles, failures, and ultimate success of building the Neoledge bilingual OCR pipeline.

1. The Beginning: Choosing the Engine

When the project started, the goal was simple: Extract Arabic and French text from scanned documents. Naturally, our first thought was to test standard, off-the-shelf OCR engines. We began by benchmarking three primary candidates: Tesseract, PaddleOCR, and EasyOCR.

The Tesseract Failure

While Tesseract performed admirably on clean English and French text, it failed catastrophically when introduced to Arabic. Because Arabic is cursive and context-dependent, Tesseract struggled to identify character boundaries, returning broken strings of disconnected letters.

The PaddleOCR Promise & Pivot

We then tested PaddleOCR. Initially, it seemed like the perfect solution. PaddleOCR was incredibly accurate when handling French documents alone, and it was equally impressive on pure Arabic documents. However, after extensive testing, we discovered a fatal flaw: Bilingual integration. When PaddleOCR attempted to read documents containing both Arabic and English text intermingled, it completely fell apart, mangling the right-to-left and left-to-right directions.

Settling on Dual Pipelines with EasyOCR

To solve the bilingual issue, we shifted our focus to EasyOCR. We found a unique approach: we divided our system into two dedicated OCR pipelines. We explicitly routed French/English documents to a specialized PaddleOCR pipeline (since it handled Latin characters perfectly), while routing Arabic/English bilingual documents to EasyOCR, which managed the complex directional shifts much more effectively.

2. Layout Parsing: The Detector Trials

Even with EasyOCR handling Arabic well, feeding an entire dense document with tables and logos into the OCR engine directly caused severe layout confusion and hallucinations.

We needed a layout parser to crop out paragraphs and tables before running OCR. We tried several object detection models: the Florence vision models, Meta's Detectron2, and the YOLO family. Florence was too slow for real-time inference, and Detectron was overly complex to configure for simple text bounding boxes.

We ultimately settled on YOLOv11s. By training a custom YOLOv11s model, we achieved lightning-fast inference to strictly crop out text paragraphs first. The layout confusion disappeared entirely.

3. The Spelling Crisis: AraBERT & RoBERTa

Even with YOLO isolating the text, EasyOCR still made minor spelling errors. We couldn't rely on simple regex to fix this.

We implemented AraBERT and RoBERTa Masked Language Modeling (MLM). We built a pipeline that detects low-confidence words, masks them, and asks AraBERT (for Arabic) or RoBERTa (for French/English) to predict the correct word based on surrounding context. We performed extensive benchmarking on this post-processing step to ensure it improved Word Error Rate (WER) without altering intended meanings.

4. Strict Dictionary Validation

Because language models can sometimes hallucinate "correct-sounding" words that weren't actually in the document, we backed up the MLM engines with a strict dictionary validation phase. Using highly curated Arabic and French dictionaries, we ensured that the final outputs consisted solely of valid vocabulary, eliminating nonsensical outputs.

5. The Final Polish: Formatting with the Gemini API

The raw text extracted by our local pipeline was accurate, but the layout formatting was lost. We needed a way to restore bolding, headers, and bullet points.

We integrated the Gemini Cloud API to act strictly as a formatting organizer. Gemini takes the perfectly extracted text from YOLO/EasyOCR, looks at the original image layout, and simply injects Markdown formatting.

6. The Heavy Weights: Colab & Qwen2-VL

For highly complex documents with nested tables and handwritten sticky notes, the local pipeline showed limits. We turned to a heavy Vision Language Model: Qwen2-VL-7B-Instruct.

Because this model required massive GPU VRAM, we engineered a secure reverse-proxy bridge using Ngrok. We hosted the heavyweight Qwen2-VL model on a free Google Colab T4 GPU, exposing an API endpoint that our local server could query. This allowed us to process massive documents without melting our local hardware.

"We hit a terrifying bug where Qwen2-VL got stuck in an infinite loop generating table separators (| | | |). We solved this by tightening the system prompt, strictly forbidding conversational filler, and saving image tensors to disk before tokenization."

7. Deployment & API Platform

After we finished the pipeline and confirmed everything was working exactly as we wanted with high precision, we needed a way to deliver it to end users. We built a comprehensive web platform using Django.

The Django platform wraps the entire complex multi-model pipeline into a single, user-friendly interface. Users simply drag and drop documents, and the backend handles all the routing between YOLO, EasyOCR, PaddleOCR, AraBERT, and Gemini automatically.

Furthermore, recognizing that this powerful pipeline could be highly valuable for other architecture and software projects, we added a developer feature: A downloadable Python API Client. By clicking the download button in the navigation bar, developers can instantly acquire a Python script pre-configured with API keys to integrate our Neoledge OCR pipeline into their own autonomous workflows seamlessly.

Conclusion

By aggressively isolating problems across six distinct architectural layers—YOLOv11s for layout, Dual EasyOCR/PaddleOCR pipelines, AraBERT/RoBERTa for spelling, Strict Dictionaries for validation, Gemini for formatting, and Colab VLM for heavy lifting—we constructed an OCR pipeline that resists hallucinations and gracefully handles dense, bilingual documents.
